# 单模块提示词模板（可直接复制）

> 本模板由 `build_prompt.py --submodule <名称>` 渲染。每次触发只生成**一段**针对单个功能子模块的提示词，
> 输出到终端（stdout），由用户复制后粘贴给 coding agent 执行。不写文件、不批量生成。
>
> 想调整措辞（例如把「你的工作」换成你们团队更习惯的表述），改 `build_prompt.py` 的
> `render_prompt()` 即可 —— 提示词正文只在这一处。

## 模板结构

**风格 A（各功能点有独立功能描述）**：

```markdown
# 功能子模块整改提示词

## 功能子模块
{功能子模块名}

## 功能点清单（共 N 个）

### 功能点 1：{功能点名称}
- 功能说明：{功能描述}
- 菜单页路径：{菜单路径}
- 测试反馈：{测试反馈}

### 功能点 2：{功能点名称}
- 功能说明：{…}
- 菜单页路径：{…}
- 测试反馈：{…}
```

**风格 B（整组共享一段功能描述 —— 源表合并单元格写在组首行）**：

描述提升为子模块级章节，功能点条目不再逐条重复。

```markdown
# 功能子模块整改提示词

## 功能子模块
{功能子模块名}

## 功能子模块简介
{组首行的功能描述}

## 功能点清单（共 N 个）

### 功能点 1：{功能点名称}
- 菜单页路径：{菜单路径}
- 测试反馈：{测试反馈}
```

## 「你的工作」段落（固定文案）

```markdown
## 你的工作
你是一名全栈开发 agent。请基于本项目（前端 + 后端 + 数据库等全栈代码），
对上述「{功能子模块名}」下的全部功能点测试反馈进行全栈改造。要求：
1. **先给出改造方案**：明确影响范围、涉及的前后端文件/接口、数据结构变更、
   实现步骤与风险；方案经确认后再动手编码。
2. **逐条对照测试反馈**：定位每条不通过的根因并修复，确保与功能说明一致。
3. **自测与验证**：修复后给出自测步骤与预期结果，说明如何在对应菜单页路径下验证。
4. 保持改动最小且聚焦本子模块，不引入无关变更。
```

## 设计要点

- **功能描述双风格**：组首行有描述、且同组其余行为空或与之相同（源表合并单元格）时用风格 B，
  否则用风格 A；全空则不显示「功能子模块简介」章节。
- **单模块即一段文本**：每次触发只产出一段自包含提示词，不含任何授权信息，可直接复制。
- **测试反馈只留关键信息**：单条功能点的测试反馈只取「测试反馈」列内容，单行呈现，避免冗余。
- **先方案后编码**：`## 你的工作` 强制「先给改造方案、确认后再编码」，降低往返试错成本。
- **按需循环**：复制 → coding agent 执行 → 验收打钩 → 下一个子模块重新触发，不做批量自动化。
- **列缺失自动降级**：`config.columns` 里置空某列时，该列既不参与筛选也不出现在提示词里，
  便于适配结构不同的表格。
